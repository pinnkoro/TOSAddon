# 新しいアドオンを追加する

手順・触るファイル・罠は [docs/NEW_ADDON.md](../../../docs/NEW_ADDON.md) に全部ある。
**まずそれを読むこと。** ここには進め方だけ書く。

## 進め方

1. **何をするアドオンかを、素の挙動から確かめる。**
   「こう動いているはず」で書き始めない。素のクライアント実装は
   `git show upstream/main:_client/jp/...` で実物を読める。**フレーム名・コントロール名・
   属性（`hittestframe` など）・関数の中身を目で確認してから設計する。**
   * 素の `.xml` は当たり判定と初期の大きさ、`.lua` は書き戻しの経路を持っている。
     **書き戻す経路を見落とすと「見た目は直ったのに当たり判定だけ戻る」形で出る。**
   * upstream のスナップショットが古くて欲しいデータが無いときは、ローカルのゲーム本体から取る
     （[docs/LEVEL_CAP_UPDATE.md](../../../docs/LEVEL_CAP_UPDATE.md) の §0）。

2. **キー・表示名・カテゴリをユーザーに確認する。**
   **キーは設定 JSON のキーでありフォルダ名でもあるので、後から変えると利用者の設定が消える。**
   こちらで案を出してよいが、確定させてから書き始める。カテゴリは
   `g._nexus_addons_p_sections` のどれか。

3. **既存アドオンと機能が被らないか、同じ素のフレームを触っていないかを grep する。**
   * `grep -rn "<フレーム名>" nexus_addons_p/src/` で先客を探す
   * `grep -rn "setup_hook.*<関数名>" nexus_addons_p/src/` で**フックの先客**を探す。
     控え（`_REPLACE_`）は素の関数 1 つにつき 1 本しか持てないので、
     **重ねると先客が黙って落ちる**
   * 先客が居たら、**どちらで折り合いを付けるかをユーザーに聞く**（§「判断を委ねること」）

4. **docs の §1 の 5 か所を上から潰す。** 本体 / アドオン README / registry（エントリ +
   3 言語の説明）/ build_manifest / 配布 README（一覧 + 更新履歴）。
   `since = g.VER_NEXT` を忘れないこと（版数は上げない）。

5. **窓を作るなら docs の §2 の 4 つを必ず通す。**
   `block_click_through` / `esc_register` 系 / `settings_frame_pos` / 検索欄の共通部品。
   ESC は **× ボタンと同じ後始末**を通すこと。

6. **docs の §3 の罠を 1 つずつ照合する。** 特に:
   * `<key>_on_teardown` を定義したなら、**機能を一度も ON にしていない利用者にも
     1 回呼ばれる**。素の UI を戻す処理は「自分が手を入れた印」で必ず守る
   * 窓を 2 枚以上持つなら、**片方を破棄する経路すべて**でもう片方も畳む
   * `local` は宣言行より後ろからしか見えない。設定の読み込みから後方の表を引くなら前方宣言

7. **検証してから `.ipf` を置く**（docs の §4）。`--bless` のあと**引数なしで再生成**すること。
   置いた `.ipf` から lua を取り出して bundle とバイト比較するまでが 1 セット。
   コピー前にクライアントを終了する（起動中はロックされる）。

8. **実機で確認する観点をユーザーに渡す。** 機械で見られるのは純ロジックだけなので、
   「何をどう触ると、どこが期待どおりか」を箇条書きで渡す。判断の材料になる値を
   `g.vlog` で 1 回だけ出しておくと、実機のログで確かめられる。

9. **PR を出す**（docs の §5）。見た目を変えたならスクリーンショット撮り直しの Issue を作り、
   **PR 本文に番号を書く**。alt テキストの更新は PR の中で行う。

## 判断をユーザーに委ねること

勝手に決めず、選択肢と理由を出して聞く。

* **見え方が変わる選択**。何を残して何を消すか、掴む場所をどこにするか、
  色や位置をどうするか。実機を見ているのはユーザーだけなので、こちらの想像で決めない。
* **既存アドオンと取り合いになったときの折り合い**。相手側に「こちらが ON なら
  何もしない」分岐を入れるのか、こちらが諦めるのか、併用不可として README に書くのか。
* **既定を ON にするか OFF にするか**（原則 OFF だが、例外を作りたくなったら聞く）。
* 素の機能を**消す**方向の変更。素にある項目を機能 OFF のときにまで消してはいけない
  （CLAUDE.md）。ON のときだけ差し替える形で足りるかを確認する。

## やってはいけないこと

* 素の関数の中身を書き写して自分の処理を足す（置換方式フックは必ず素を呼ぶ）
* 版数を上げる（採番は `release-prep/vX.Y.Z` だけ）
* 生成物の bundle `.lua` を直接編集する（編集は `src/**` 側）
