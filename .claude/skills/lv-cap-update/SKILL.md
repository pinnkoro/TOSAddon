# レベル上限の解放に追従する

手順・触るファイル・罠は [docs/LEVEL_CAP_UPDATE.md](../../../docs/LEVEL_CAP_UPDATE.md) に全部ある。
**まずそれを読むこと。** ここには進め方だけ書く。

## 進め方

1. **何が追加されたかをユーザーに確認する。** 新レイド名 / 新クラス名と Lv 帯。
   ID は聞かない（こちらで取れる）。**ただし「1 つ増えた」と言われても実データを見ると
   複数増えていることがある**ので、`indun.ies` を見てから対象範囲を確認し直す。

2. **ID を実データから取る。** upstream の `_client/**` は古いので使わない。
   ローカルのゲーム本体を `tos_extract.py` で読む（場所と手順は docs の §0-1）。
   **既存の ID が消えていないかも必ず確認する**（Lv560 では 1005 が消えていた）。

3. **docs の §2 の表を上から潰す。** 触り忘れが出やすいのは
   `indun_keys` / `cols` のバックフィル、`indun_list_viewer` の `ver` 繰り上げ、
   `vlog_new_induns` の `targets`。

4. **罠（docs §3）を 1 つずつ照合する。** 特に:
   * `itemtradeshop.ies` の `TargetItem` が差し替わっていないか
   * Hard が未実装のレイドがないか
   * ボス / ショップのアイコンが使い回しで見分けが付かなくならないか
   * 新クラスは `skill_gem_tooltip` の `job_name_fix_map` が要るかだけ機械的に判定する

5. **「ID を表に足した」で終わりにしない。その表を読む側を全部たどる。**
   足した表が読まれる経路が 1 つとは限らず、**別の経路が別の表を見ていること**がある。
   Lv560 では `quickslot_operate_raid_list` に足したが、マップ監視側は
   手書きのマップ ID 一覧を見ていたため、新マップでは効かなかった。
   * 表を読む関数を grep し、**呼び出し元を全部**確認する
   * その経路が**必ず通るか**を確かめる。素の関数がクライアント Lua に実体を持たない
     （`ReqRaidAutoUIOpen` など）なら静的には確かめられないので、**断定せず、
     詳細ログで実機確認する手順を利用者に渡す**
   * 手で足すマップ ID / クラス ID の一覧を見つけたら、**既存のデータから導けないか**を
     先に疑う（導ければ次回から手入れが要らなくなる）

6. **検証してから `.ipf` を置く**（docs §4）。`--bless` のあと**引数なしで再生成**すること。
   置いた `.ipf` から lua を取り出して bundle とバイト比較するまでが 1 セット。

7. **更新履歴・NEW/Update の印・各 README・alt テキストを更新し、
   スクリーンショット撮り直しの Issue を立てる**（docs §5）。版数は上げない。

## 判断をユーザーに委ねること

* 画面が横に広がる、アイコンの見た目が変わるなど**見え方が変わる選択**
* 新コンテンツのうちどこまで対応するか（レイド以外のパーティダンジョンなど）

勝手に決めず、選択肢と理由を出して聞く。
